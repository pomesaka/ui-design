# ui-design:review

判断基準は書き写さず、ui-designの文書を正本として読む。採用先で使うときは、作業前にそれらの文書を読める場所(複製・submodule等)を確かめる。

- [DESIGN.md](../../DESIGN.md)と[画面の組み立て方](../../docs/composition.md)
- [部品の一覧と結果の伝え方](../../components/README.md)、[tokenの役割](../../tokens/README.md)

## 入力

- 対象:URL、画面のファイル、差分のいずれか
- 利用者と目的:依頼や画面の文書に無ければ、内容から推測して書き出し、仮定であると明示する
- 状態の出し方(URL引数等)とテーマ名(`themes/`のファイル名)

## 手順

1. 利用者ごとのストーリーを書き、[三つの問い](../../docs/composition.md#利用者から始める)を評価の軸にする。
2. 描画して撮る。このファイルと同じ場所の`node scripts/capture.mjs <出力先> <URL>... --themes <テーマ,...> --wait <描画完了のselector>`で幅390・768・1280px × 各テーマを撮り、全画像を見る。空・失敗・長い内容・大量の件数等の状態はURLを並べて撮る。`--text-scale 2`で文字200%も撮る。ログインが要る画面は`--storage-state`、内側の要素がスクロールする画面は`--scroll <selector>`を使う。Playwrightが見つからないworkspaceでは、Playwrightを依存に持つpackageから実行するか`NODE_PATH`を渡す。
3. 操作する。Playwright等で実際に操作し、値で確かめる。
   - keyboardだけで主操作まで届くか。操作で要素が消えたり閉じたりした後、`document.activeElement`がbodyに落ちず意味のある場所にあるか。
   - 結果の伝わり方。画面の変化、Banner・Notice、live regionに入った文言。
   - `reducedMotion: "reduce"`で開いても、同じ操作が同じ結果に届くか。animationの完了を待たないと操作できない箇所がないか。
4. コードを見る。部品の使いどころ、variant、tokenの対の組合せ、token外の値、`as`による型の断定。このrepository内なら`bun run check`も実行する。
5. 文書の決定と[避けるもの](../../docs/composition.md#避けるもの)に照らす。文書で決まっていない判断は、指摘ではなく提案として分ける。

## 出力

重大な順に並べる。各指摘に次を書く。

- 重大度
  - 阻害:目的を終えられない(操作に届かない、結果が失われる、読めない)
  - 迷わせる:終えられるが迷う・見失う(focusの消失、結果が見えない、名前で区別できない)
  - 不一致:規則や見た目が文書・tokenと合わない
- 場所(ファイル:行、画面と状態、スクリーンショットのパス)
- 根拠(文書の節、測った値)と、修正案

最後に、確かめた範囲と確かめていない範囲を分けて書く。確かめていない範囲の典型は、実機のタッチと仮想keyboard、実際のスクリーンリーダー、Chromium以外のブラウザ、ブラウザ自体の文字拡大、描画負荷。修正は頼まれたときだけ行う。
