# 開発方針

## 資産を追加する

用途・必要な状態・操作・アクセシビリティを説明でき、製品固有の用語・データ・画面遷移へ依存しない範囲を収める。採用先の条件まで多数のoptionへ押し込まず、実利用から共通の境界を見つける。

部品には、カタログで実際に触れる代表例と、スクリーンショットで一度に比較できる状態一覧を用意する。hover・pressed・focus-visible等は操作せず見える固定見本を並べ、実操作と同じstyleを使う。明暗・幅・長い内容・pending・empty・error等から、その部品に意味のある状態を選ぶ。使いどころ・制約は原本の近くに残す。
スキルには利用場面・必要な入力・手順・期待する出力を記し、デザイン基準は`DESIGN.md`を参照する。プロンプトは利用するskillのそばに置く。
外部のコードや素材を取り込む場合は、出典と利用条件を確認し、必要な表示・文書を保持する。

## 検証する

テーマを追加・変更したら`bun run check:themes`で名前の過不足・参照を確認する。検査スクリプトの回帰は`bun test scripts/check-themes.test.mjs`で確認できる。どちらも追加依存は不要。[テーマの手順](../themes/README.md)に従い、CSS構文・計算値・contrast・実操作は別に確認する。

- 文書・指示だけの変更は内容・参照・整合を確認する。
- 実装は採用したtoolの静的検査と、変更に関係する振る舞いを確認する。起動・build・検査のcommandは、実装に合わせてrepository内に定義する。
- UIは実部品のカタログで、表示だけでなく選択・入力・focus・scroll・閉じる操作を確認する。touch・端末権限・性能は、必要なbrowserや実機で確かめる。
- テストは防ぎたい不具合を説明できる境界へ置き、実装やCSS classの写しを増やさない。条件比較は可能ならtable drivenにする。
- スキルは代表的な依頼で試し、手順を読めることと、期待する判断・出力が得られることを分けて確認する。

## 文書を置く

制約は型と構造、振る舞いはテスト、実装を変える人に必要なWHYはコメントへ置く。文書にはコードを読む前に要る概念・横断の約束・手順だけを残し、変更の経緯と検証結果はcommit・PRへ書く。
同じ規則は一か所に置き、他からリンクする。READMEは入口に留め、作業履歴や未実装機能の一覧にしない。
